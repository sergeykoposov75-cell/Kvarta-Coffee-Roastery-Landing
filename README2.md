Процесс работы и использование ИИ

Что делал сам:

Изучил ряд сайтов локальных обжарок и студий, чтобы выявить типичные «штампы» (стоковые фото чашек на столе, слова вроде «премиальный» и «индивидуальный подход») и избежать их.

Спроектировал визуальную концепцию:  определил палитру (тёплые, землистые тона вместо стандартных IT-градиентов) и продумал структуру, отличную от типовых шаблонов.

Провел финальный аудит контента: поручил убрать всё, что звучало «сгенерированно», и добавил № телефона для заказов.

Что делал ИИ (с моим контролем):

DeepSeek: использовал для генерации плана проекта, проработки архитектуры компонентов и написания системных промптов для KodaCode.

KodaCode: использовал как исполнителя для генерации кода на Next.js и Tailwind, верстки компонентов и настройки API-роутов. Всю работу вел через сессии, выдавая агенту конкретные задачи и разрешения (Auto-режим).

Где ИИ ошибался и как я это заметил:

Дизайн-клише: Первый сгенерированный вариант Hero-секции выглядел слишком стерильно и шаблонно. В промпте указал на более «живую», редакторскую подачу.

Тексты: Агент несколько раз пытался вставить фразы вроде «широкий ассортимент» или «команда профессионалов». Замечал это и заставлял переписывать, добавляя конкретику из ТЗ.

Что не успел или сделал бы иначе:

Не успел: Полноценно протестировать интеграцию с Telegram-ботом вживую (с реальным токеном), так как фокусировался на обязательных требованиях и базовой форме. Анимации также оставили в минимальном объеме, чтобы не просадить Performance в Lighthouse.

Сделал бы иначе: Если бы было больше времени, заменил бы фото со стоков на реальную предметную съемку или сгенерировал бы кастомные 3D-мокапы пачек, чтобы сайт выглядел еще более уникальным. Также добавил бы более сложную логику дедупликации заявок (например, с привязкой к IP).

NB: К сожалению, в процессе упустил указание в ТЗ о коммитах по шагам, т.к. производилось довольно много правок. Надеюсь, это компенсируется файлом session_report.md с пошаговым описанием сессий проекта.


# Кварта — лендинг обжарки кофе

Одностраничный лендинг вымышленной минской обжарочной «Кварта»: свежая
обжарка по четвергам, доставка по пятницам. Форма заявки с защитой от ботов,
UTM-атрибуцией, сохранением лидов и Telegram-уведомлениями.

**Живой сайт:** https://kvarta-landing.vercel.app _(замените на реальный домен после деплоя)_

## Стек

- Next.js 14 (App Router, TypeScript) — статическая страница + один API-роут
- Tailwind CSS — дизайн-система (палитра, типографика Lora/Inter, сетка 12 колонок)
- better-sqlite3 — локальное хранилище лидов
- @vercel/kv — хранилище лидов в продакшене
- Telegram Bot API — уведомления менеджеру

## Запуск

```bash
npm install
npm rebuild better-sqlite3   # нативный модуль под текущую платформу
npm run dev                  # http://localhost:3000
```

Сборка и проверки: `npm run build`, `npm run typecheck`, `npm run lint`.

## Переменные окружения

Скопируйте `.env.example` в `.env.local`. Обязательны только две — для
уведомлений (без них заявки просто не дублируются в Telegram):

| Переменная           | Назначение                                        |
| -------------------- | ------------------------------------------------- |
| `TELEGRAM_BOT_TOKEN` | токен бота от @BotFather                          |
| `TELEGRAM_CHAT_ID`   | chat_id получателя заявок                         |

Опционально: `LEAD_FORM_SECRET` (соль для хешей IP/телефона), `SQLITE_PATH`,
`KV_REST_API_URL` / `KV_REST_API_TOKEN` (включают KV-режим),
`NEXT_PUBLIC_SITE_URL` (абсолютные URL в meta/openGraph).

На Vercel переменные добавляются в Project → Settings → Environment Variables.

## Хранение заявок: почему так

- **SQLite локально** — ноль внешних зависимостей в разработке: файл
  `data/leads.db` создаётся сам, запросы смотрятся утилитой `sqlite3`.
  Для лендинга с десятками заявок в день этого более чем достаточно.
- **Vercel KV в продакшене** — у serverless-функций Vercel нет постоянного
  диска: файл SQLite переживёт один холодный старт и исчезнет. KV —
  управляемое хранилище «в той же экосистеме», с TTL и без отдельного
  провайдера. Ключи: `lead:<id>` (полная карточка, TTL 400 дней),
  `leads:phone:<hash>:<дата>` (индекс дедупликации).

Оба бэкенда реализуют один интерфейс `LeadRepository` (`lib/storage.ts`),
переключение — по наличию переменных KV.

## Защита и обработка заявок

1. **Honeypot** — скрытое поле `company`: заполнено = бот, тихий 200 OK.
2. **Temporal guard** — отправка раньше 3 секунд после рендера отклоняется.
3. **Rate limit** — не больше 3 отправок с одного IP за 10 минут.
4. **Дедупликация** — заявка с тем же номером телефона в течение
   **10 минут** не создаёт новую запись (защита от двойного нажатия),
   возвращается 200 OK без дубля в базе и без второго уведомления.
5. **Telegram** — после сохранения POST в Bot API; ошибки только логируются
   и не влияют на ответ формы.

## Трекинг источников

`utm_*` из URL и `document.referrer` ловятся при первом посещении
(`lib/utm.ts`), сохраняются в **sessionStorage** (`kvarta:utm`) и вместе с
`referrer` и URL страницы уезжают в **API** (`/api/lead`). По utm_source /
referrer определяется канал: `instagram` / `google` / `direct` / `other` —
он пишется в поле `traffic_source` и виден в Telegram и в базе. Прямые
переходы без меток не перезаписывают уже сохранённую атрибуцию.

## Допущения

- **Клиент вымышленный**: «Кварта», Аня и Дмитрий, адрес, телефоны и цены —
  демонстрационные. Перед запуском заменить на реальные.
- **Фото — Unsplash** (бесплатная лицензия). Заменить на съёмку
  обжарочной при появлении материалов.
- **Логотип — текст** («Кварта», Lora). Фирменный знак не разрабатывался;
  favicon — текстовая «К».

## Аудит на «AI-шаблонность»

- **Стоп-слова** («премиальный», «уникальный», «инновационный»,
  «качественный», «надёжный», «команда профессионалов», «индивидуальный
  подход», «широкий ассортимент», «гибкие условия») — не встречаются
  (проверено поиском по исходникам).
- **Конкретика в каждом блоке**: Hero — «1–3 дня», имена; About — Аня и
  Дмитрий, 2019 год, партии по 5 кг, четверг; Products — цены в BYN, вес
  250 г, ноты; Subscription — 2×250 г, 54 BYN/мес; Delivery — адрес
  «ул. Короля, 9», часы работы, «от 50 BYN бесплатно», телефон.
- **Детали контакта**: телефон, адрес, часы, имена, год основания, вес
  партии — присутствуют.
- **Нешаблонный порядок секций**: Hero → About → Products → Subscription →
  Delivery → Form (не Hero → Features → Testimonials → CTA).

## Структура

```
app/
  layout.tsx            — мета (title, openGraph, twitter), шрифты, иконки
  page.tsx              — сборка секций
  api/lead/route.ts     — приём заявки: honeypot → temporal → валидация
                          → rate limit → дедуп → сохранение → Telegram
components/             — Header, Hero, About, Products, Subscription,
                          Delivery, LeadForm, Footer, Section, Reveal
lib/
  validation.ts         — телефон BY, имя, интерес (одни правила для
                          клиента и сервера)
  storage.ts            — репозиторий лидов: SQLite (dev) / Vercel KV (prod)
  utm.ts                — атрибуция: utm_* + referrer → канал трафика
  telegram.ts           — уведомления о заявках (ошибки не блокируют форму)
types/lead.ts           — модель лида и контракты API
```
